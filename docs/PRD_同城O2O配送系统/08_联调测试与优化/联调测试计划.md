## 一、联调范围

### 1.1 终端联调矩阵

| 联调组合 | 涉及终端 | 核心验证点 |
|----------|----------|------------|
| 用户下单→商家接单 | 小程序 ↔ 商家APP ↔ 后端 | 订单创建、支付回调、商家通知、接单响应 |
| 商家接单→骑手配送 | 商家APP ↔ 骑手APP ↔ 后端 | 订单池推送、抢单、取货确认、配送状态 |
| 用户→骑手配送追踪 | 小程序 ↔ 骑手APP ↔ 后端 | 实时位置、轨迹展示、预计到达 |
| 用户售后→后台处理 | 小程序 ↔ 管理后台 ↔ 后端 | 退款申请、审核、退款执行 |
| 后台管控→各端联动 | 管理后台 ↔ 小程序/商家APP/骑手APP | 封禁联动、配置联动、消息通知 |
| 微信端→小程序跳转 | 微信端 ↔ 小程序 | 分享链接、消息跳转、授权衔接 |

### 1.2 联调优先顺序

```
第1轮：核心主流程贯通
  └── 商品订单：下单→支付→商家接单→骑手抢单→取货→配送→送达→确认
  └── 跑腿订单：发单→支付→骑手抢单→执行→完成→确认

第2轮：分支流程验证
  └── 商家拒单/超时 → 自动退款
  └── 用户取消 → 退款
  └── 骑手异常上报 → 客服介入
  └── 售后退款全流程

第3轮：配置与管控联调
  └── 后台配置变更 → 各端生效
  └── 后台审核操作 → 各端状态更新
  └── 后台封禁/冻结 → 各端登录/操作受限

第4轮：消息通知验证
  └── 全链路消息触点验证（小程序消息/APP推送/站内消息）

第5轮：边界与异常场景
  └── 并发抢单
  └── 支付回调延迟
  └── 网络异常
```

## 四、Bug管理规范

### 4.1 Bug优先级定义

| 优先级 | 定义 | 修复要求 | 举例 |
|--------|------|----------|------|
| P0-阻断 | 核心功能不可用，无法继续测试 | 立即修复，4小时内 | 无法下单、支付失败、无法登录 |
| P1-严重 | 主要功能异常，有变通方案 | 24小时内修复 | 退款金额错误、状态流转异常、通知不到达 |
| P2-一般 | 次要功能异常或体验问题 | 48小时内修复 | UI错位、排序不生效、搜索条件异常 |
| P3-轻微 | 文案、样式等不影响功能的问题 | 上线前修复 | 错别字、颜色不一致、间距不均 |

### 4.2 Bug记录模板

```
## Bug标题：[终端][页面] 问题简述

**优先级：** P0/P1/P2/P3
**终端：** 小程序/商家APP/骑手APP/管理后台/后端
**页面/接口：** 具体页面或接口路径
**环境：** 测试环境/设备型号/系统版本/浏览器版本
**复现步骤：**
1. 步骤1
2. 步骤2
3. 步骤3

**预期结果：** ...
**实际结果：** ...
**截图/视频：** （附件）
**关联用例：** GO-01/ER-03 等
```

### 4.3 Bug修复与回归流程

```
发现Bug → 记录Bug → 分配开发 → 开发修复 → 提交代码
→ 部署测试环境 → 测试回归验证 → 通过则关闭 → 未通过则重新打开
```

### 4.4 回归测试策略

- P0/P1 Bug修复后，必须回归关联的核心主流程用例
- P2 Bug修复后，回归该Bug涉及的功能点
- 每轮Bug修复完成后，执行全量P0用例回归
- 上线前执行最终一轮全量回归
