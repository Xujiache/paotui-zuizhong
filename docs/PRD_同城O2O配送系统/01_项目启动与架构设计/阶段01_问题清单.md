## P0 阻塞型问题

### P0-1 管理后台响应体契约与后端/PRD 不一致
- **现象**：管理后台仍沿用 `art-design-pro` 模板的响应格式。
- **期望**（PRD《接口规范与状态机.md》§1.1）：`{ code: 0, message: string, data: any }`，成功码为 `0`。
- **实际**：
  - `管理后台/src/types/common/response.ts` 定义 `BaseResponse` 字段为 `msg` 而不是 `message`。
  - `管理后台/src/utils/http/status.ts` 定义 `ApiStatus.success = 200` 而不是 `0`。
  - `管理后台/src/utils/http/index.ts` 第 86、87 行使用 `response.data.msg` 和 `code === ApiStatus.success` 判断成功。
- **影响**：后端返回的 `code: 0` 会被管理后台判定为"业务失败"，Phase 02 一联调就崩。
- **修复建议**：
  1. `BaseResponse` 字段 `msg` 改 `message`（并全局替换引用）。
  2. `ApiStatus.success` 改为 `0`；HTTP 状态码改名到 `HttpStatus` 常量区分。
  3. `http/index.ts` 响应拦截器根据 `code === 0` 判成功，并显示 `response.data.message`。
  4. `http/error.ts` 相关引用同步修正。

### P0-2 管理后台 API 路径缺 `/v1/` 版本号前缀
- **期望**（PRD §5.1）：所有接口 `/api/v1/{service}/{resource}`。
- **实际**：
  - `管理后台/src/api/auth.ts`：`/api/auth/login` 和 `/api/user/info`
  - `管理后台/src/api/system-manage.ts`：（需排查）
- **修复建议**：全局替换 `/api/` → `/api/v1/`；用户信息接口按 PRD 归到 `/api/v1/admin/profile` 或 `/api/v1/auth/me`。

### P0-3 管理后台 `Api` 命名空间类型与后端契约不符
- **现象**：`管理后台/src/types/api/api.d.ts` 仍是模板原厂定义。
- **实际 vs PRD**：
  | 字段 | 实际（模板） | PRD 规范 |
  |------|--------------|----------|
  | 分页入参 | `current`, `size` | `page`, `pageSize` |
  | 分页响应 | `records[]`, `current`, `size`, `total` | `list[]`, `pagination.{page,pageSize,total,totalPages}` |
  | 登录响应 | `{ token, refreshToken }` | `{ accessToken, refreshToken }`（与 `node后端/src/utils/jwt.ts` 对齐） |
  | UserInfo | `userName`, `userId`, `buttons` | 需按 Phase 03 约定 |
- **修复建议**：重写 `api.d.ts`，按 PRD 分页 + 双令牌字段重建 `Api.Common` 与 `Api.Auth` 命名空间；`system-manage.ts` 里用到旧字段的地方同步改掉。

### P0-4 uni-app x 三端请求基址硬编码
- **现象**：
  - `商家端/api/request.uts` 第 1 行 `const BASE_URL = 'http://localhost:3000'`
  - `骑手端/api/request.uts` 同上
  - `微信小程序（用户端）/api/request.uts` 同上
- **问题**：每端都有 `.env.example`（`VITE_API_BASE_URL`），但代码没读取；换环境（测试/生产）要改源码。
- **修复建议**：
  1. 方案 A（推荐）：新增 `<端>/env.js` 导出按 `process.env.NODE_ENV` 切换的 baseURL 常量，`request.uts` 引用（uni-app x 对 `.env.*` 支持有限，常用做法是写在 `env.uts`）。
  2. 方案 B：用 HBuilderX 的条件编译 `#ifdef MP-WEIXIN` 分别定义。
  3. 注意接口路径在调用处写成 `/api/v1/...`，基址只到 `http://host:port`。

### P0-5 管理后台缺 `.env.example`
- **现象**：`管理后台/` 目录下有 `.env / .env.development / .env.production`，但没有 `.env.example`。
- **验收标准 C-06**：要求 `.env.example 文件存在`。
- **额外问题**：`.env.production` 的 `VITE_API_URL = https://m1.apifoxmock.com/m1/6400575-6097373-default` 是 `art-design-pro` 原厂 Mock 地址，必须清掉。
- **修复建议**：
  1. 新建 `管理后台/.env.example`，列出 `VITE_VERSION / VITE_PORT / VITE_BASE_URL / VITE_ACCESS_MODE / VITE_WITH_CREDENTIALS / VITE_OPEN_ROUTE_INFO / VITE_LOCK_ENCRYPT_KEY / VITE_API_URL / VITE_API_PROXY_URL / VITE_DROP_CONSOLE` 空值模板。
  2. `.env.production` 的 `VITE_API_URL` 改为占位（例如 `https://api.example.com`）或留空并加注释。

## P1 违反规范但不阻塞启动

### P1-1 后端目录结构与规范文档不完全一致
- **规范要求**（《开发环境与项目规范.md》§2.2）：
  - `src/config/database.ts` 和 `src/config/redis.ts` 作为**独立**配置文件
  - `src/types/request.d.ts`, `src/types/response.d.ts` 独立类型文件
  - `src/utils/orderNo.ts`, `src/utils/validate.ts` 独立工具
  - `tests/` 下有 `unit/integration/helpers` 子目录
- **实际**：
  - 配置都塞在 `src/config/index.ts`，数据库/Redis 的连接实例放在 `src/utils/database.ts`、`src/utils/redis.ts`（功能上 OK 但和规范描述的分层不一致）
  - 类型只有 `enums.ts / express.d.ts / index.d.ts`
  - `helpers.ts` 里内联了 `generateOrderNo`
  - 无 `validate.ts`
  - `tests/` 下只有一个 `.gitkeep`
- **修复建议**（二选一）：
  1. 按规范拆分（推荐）：新建 `config/database.ts`、`config/redis.ts`（导出只读配置对象）；把连接逻辑留在 `utils/`；从 `helpers.ts` 抽 `orderNo.ts`；创建 `utils/validate.ts` 空壳（内部放常用校验器如 `isPhone/isIdCard`）；创建 `types/request.d.ts`、`types/response.d.ts` 占位；建 `tests/unit/`、`tests/integration/`、`tests/helpers/` 三个子目录各放 `.gitkeep`。
  2. 更新规范文档（如果团队确认不再拆分），但这会降低 Phase 02 开发者按图索骥的便利性。

### P1-2 后端错误码枚举不全
- **PRD §2**：12000-23099 各服务域错误码已全部列出（12 个服务域）。
- **实际**：`src/types/enums.ts` 的 `ErrorCode` 只覆盖到 `11007`。
- **修复建议**：把 PRD §2.4~§2.15 的错误码补齐到 `ErrorCode` 枚举（或拆成 `AuthErrorCode / UserErrorCode / MerchantErrorCode ...`，按服务域分文件）。Phase 01 可只列枚举值不用使用。

### P1-3 OrderStatus 枚举未按订单类型分组
- **现象**：`enums.ts` 中 `OrderStatus` 把商品订单和跑腿订单的状态混在一起，虽然注释能区分，但：
  - 缺少 `PAID`（已支付）这类在 PRD 状态机里有的状态
  - `IN_PROGRESS`、`RIDER_ACCEPTED` 和 `ON_THE_WAY` 的归属不清晰
- **修复建议**：参考 PRD《接口规范与状态机.md》§三"订单状态机"把状态值按"共用 / 商品订单 / 跑腿订单"三块整理，并与 PRD 状态图逐一对齐。

### P1-4 uni-app x 登录页未对齐 PRD 登录方式
- **PRD 用户端**：主登录方式是"微信授权一键登录"（`uni.login` + `uni.getUserProfile` → 后端 `code2session`），手机号验证码为次选。
- **实际**：`微信小程序（用户端）/pages/login/login.uvue` 只放了手机号+密码输入框。
- **PRD 商家端/骑手端**：手机号+验证码登录（支持密码登录作为备选）。
- **实际**：商家端、骑手端只有手机号+密码，缺"获取验证码"占位。
- **修复建议**：三端 login 页补充"微信一键登录"按钮或"获取验证码"按钮占位（可调用 `uni.showToast('Phase 02-03 实现')`）。

### P1-5 缺少根目录 `.gitattributes`
- **现象**：`git diff` 显示 4 个 `.env.example` 等文件因 LF/CRLF 差异被标记 modified，实际内容相同。
- **修复建议**：新增根目录 `.gitattributes`：
  ```
  * text=auto eol=lf
  *.bat text eol=crlf
  *.cmd text eol=crlf
  *.ps1 text eol=crlf
  *.sh text eol=lf
  ```
  并在仓库根目录执行一次 `git add --renormalize .` 然后 commit。

### P1-6 根目录缺项目启动 README
- **现象**：根目录没有 `README.md`，每个子项目的 README 都是默认模板。
- **PRD**：规范文档里有启动步骤，但新人第一眼看不到入口。
- **修复建议**：新建根目录 `README.md`，简要说明：项目简介、技术栈、目录结构、如何启动五端、文档位置（指向 `docs/PRD_同城O2O配送系统/`）。

### P1-7 CI 覆盖范围不足
- **现象**：`.github/workflows/ci.yml` 只对 `node后端` 跑 lint+build，对 `管理后台` 只跑 build。
- **修复建议**：
  1. 管理后台追加 `pnpm lint`（当前 `package.json` 有 `lint` 脚本）。
  2. 考虑对 uni-app x 三端做 `tsc --noEmit` 做类型预检（需要先给它们加 dev dep `typescript`）。
  3. `fail-fast: false` 让多 job 独立失败可见。

### P1-8 健康检查路径与 PRD 不完全一致
- **PRD**《基础服务开发任务.md》§示例：`GET /api/v1/common/health`。
- **验收标准 S-04**：`GET /api/v1/health`。
- **实际**：后端实现 `GET /api/v1/health`（与验收标准一致，但与基础服务任务文档的"common"前缀不一致）。
- **修复建议**：统一路径。建议保留 `/api/v1/health`（符合 Phase 01 验收），顺手在《基础服务开发任务.md》里把 `common/health` 改成 `health`，或在 `routes/index.ts` 再挂一个 `/api/v1/common/health` 作为别名。

### P1-9 老 JavaScript 代码未从磁盘清理
- **现象**：`.gitignore` 已忽略，但磁盘上还有：
  - `node后端/app.js`（根目录老版）
  - `node后端/server.js`（根目录老版）
  - `node后端/README.md`（描述的是旧版）
  - `node后端/config/index.js`
  - `node后端/middlewares/*.js`
  - `node后端/utils/*.js`
  - `node后端/scripts/initDB.js`, `initDbData.js`
- **影响**：新成员看到会困惑；与 PRD 目录结构不一致。
- **修复建议**：直接删除上述老文件和目录；`node后端/.gitignore` 第 32-38 行针对老代码的忽略规则可一并删除。

### P1-10 Phase 03 前要预留的 OpenAPI/接口文档未骨架化
- **PRD**《07_平台管理后台开发/README.md》要求 "后端接口文档（Swagger/Apifox）已发布"。
- **实际**：后端没有集成 `swagger-ui-express` 或 `@nestjs/swagger`（此项目用 Express），也没有放 `openapi.yaml`。
- **修复建议**（可放到 Phase 02 起始，但 Phase 01 骨架里最好先加）：
  1. 在 `node后端/package.json` 加 `swagger-ui-express` 依赖（`npm i -D @types/swagger-ui-express`）。
  2. 在 `src/routes/index.ts` 挂 `/api/docs`。
  3. 新建 `docs/api/openapi.yaml` 空壳。

## P2 清理/完善项

### P2-1 `.cursor/mcp.json` 和 `.cursor/rules/my-mcp.mdc` 未入库
- **现象**：git 显示 `.cursor/mcp.json` modified、`.cursor/rules/my-mcp.mdc` untracked。
- **建议**：这些属于"本地工具配置"，不建议入库；可考虑把 `.cursor/` 加入 `.gitignore`（根 `.gitignore` 第 43 行已有注释版），或者规范团队只共享 `.cursor/rules/`（不含 mcp.json）。

### P2-2 管理后台 UI 仍是 art-design-pro 原厂品牌
- **现象**：登录页、Logo、标题、HTML `<title>` 均未替换为"同城O2O配送"。
- **建议**：Phase 01 允许沿用模板，但至少把 `index.html` 的 `<title>` 改掉，`public/` 下的 favicon 换掉，登录页左侧宣传图/slogan 改成项目品牌。

### P2-3 各子项目 README 是默认模板
- **现象**：`商家端/README.md`、`骑手端/README.md`、`微信小程序（用户端）/README.md` 都是 uni-app x 模板默认内容。
- **建议**：改成本项目说明（项目名、用途、如何在 HBuilderX 打开、如何编译到微信小程序 / Android / iOS）。

### P2-4 `node后端/package.json` 的 `main` 字段
- **现象**：`"main": "dist/server.js"`，但项目是服务型应用，`main` 基本不会被外部 `require`。
- **建议**：可保留；或改成 `private: true` 并去掉 `main`（更符合服务型项目）。

### P2-5 HBuilderX 版本兼容声明
- **验收标准 E-13**：要求 HBuilderX ^4.66。
- **实际**：三个 uni-app x 项目的 `manifest.json` 没有标注版本/兼容最低要求。
- **建议**：虽然 `manifest.json` 不强制写版本要求，但可以在 README 里明确写"请使用 HBuilderX ^4.66 开发"，并让开发者自行升级。

### P2-6 微信端（原生）无 `wx.login` / 订阅消息示例
- **现象**：`微信端/pages/login/login.js` 只是空壳 `Page({})`。
- **建议**：按 PRD《微信端页面开发任务.md》在登录页放一个 `wx.login` + 模板消息订阅的占位实现（里面写 TODO，Phase 02-03 实现）。

### P2-7 未提交改动
- **4 个 `.env.example`**：内容与 HEAD 相同，只是 CRLF 差异；P1-5 解决后会消失。
- **`.cursor/mcp.json`**：本地工具配置，见 P2-1。
